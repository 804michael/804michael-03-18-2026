# Site Design/Typography Notes — 804re.com

Standing conventions and decisions captured here so future page work (by Claude or otherwise) stays consistent, without re-litigating them each time.

## STANDING RULE: tool hints and microcopy are terse, not grammatical (added 2026-09-06)

Michael, in his own words: *"I don't need no proper english in tool hints and
such. minimizing words in those types of things."*

Placeholders, button hints, inline captions, validation messages and empty
states are **labels, not prose**. Articles, hedges and polite scaffolding cost
width in exactly the places that are tightest - a placeholder inside a narrow
input, a hint under a button, a caption on a phone - and read as padding rather
than manners.

**Trim:** "the", "a", "at least one", "you want to", "then ... can be",
"in the right order", "just", "please".

| Was | Now |
| --- | --- |
| Publish to create the link | Publish to create link |
| Add at least one stop first. | Add a stop first. |
| Give this tour a name first. | Name the tour first. |
| Calculate a route first, so the stops publish in the right order. | Calculate a route first, so stops publish in order. |
| Anything you want to remember about this one | Anything to remember about this one |
| Drag cards to reorder | Drag to reorder |

**This does NOT apply to visitor-facing page copy.** A guide page, a locality
page, the client tour page's own explanatory sentences - those stay written in
full sentences. The rule is specifically about UI chrome: the words wrapped
around a control, where the control is the message and the text is a label for
it. A good check: if it sits inside, on, or immediately under an input or
button, trim it. If it is something a person reads for its meaning rather than
to operate something, leave it.

Two carve-outs that stay long on purpose, because they are disclosures rather
than labels: the publish note on the route planner ("Publishing sends addresses
& client notes only...") and the privacy line on the client tour page ("Your
ratings and notes are saved and shared with Michael..."). Being terse there
would cost clarity about who sees what, which is the one thing those sentences
exist to make unambiguous.

## STANDING RULE: responsive floor is 320px, and Michael's real devices (added 2026-09-05)

**Michael's current devices** (these replace the older `804len-book14` reference
further down):

- **Lenovo Yoga Book, product 83KJ0001US, Windows 11** - desktop work
- **Samsung Galaxy S24 Ultra** - approx **412 x 915 CSS px** in the browser

Test mobile work at **412px**, not the 375px iPhone default, because that is the
phone actually in his pocket.

**Support floor: 320px.** Every layout must work, with no sideways page scroll
and no clipped text, from 320px up. That covers effectively every phone of the
last five years:

| Width | Devices |
| --- | --- |
| **320px** | iPhone SE (1st gen) - the practical floor |
| 344px | Galaxy Z Fold cover screen (folded) |
| 360px | Galaxy S/A series, most budget Android |
| 375px | iPhone SE (2nd/3rd gen), iPhone 12/13 mini |
| **412px** | **Galaxy S24 Ultra - Michael's phone** |
| 430px | iPhone 15/16 Pro Max |

Anything narrower than 320px is not supported and is not worth designing for.

**Verify at 320, 344, 412 and 430 at minimum.** 320 and 412 catch the most: 320
is where text runs out of room, 412 is what Michael will actually look at.

### The specificity trap that made this necessary

The mobile summary-row rules on `tour-planner.html` were originally written into
an `@media(max-width:640px)` block that sat **above** the base
`.tp-summary-stat` rules in the stylesheet. A media query does not add
specificity - on a tie, the rule that comes **later in source order** wins - so
those mobile rules never applied at any width. Nobody noticed because the flex
layout still fit; the labels were simply rendering at the desktop size and
wrapping to three and four lines in a 65px column.

**When adding a responsive override, check where the base rule lives and put the
override after it.** There is already a comment near line 660 of
`tour-planner.html` warning about this exact tie-break; it was written for a
different bug and applies generally.

### Narrow-screen technique used here

Rather than shrink long labels until they wrap into ribbons, each figure in the
summary row carries two labels in the markup - `.lbl-long` and `.lbl-short` -
and `@media(max-width:480px)` swaps which one displays. At 320px this took the
label block from 56px tall (four wrapped lines) to 11px (one line), and the
whole row from 79px to 62px. Prefer this over font-shrinking whenever a label
has a natural short form.

## STANDING RULE: never read-and-rewrite these files through PowerShell or as UTF-8 (added 2026-09-05)

The HTML in this repo is **not valid UTF-8**. It is mixed content with
Windows-1252 bytes in it, and always has been. That is fine in a browser (the
pages declare `charset=UTF-8` and render correctly), but it makes the files
fragile to any tool that decodes and re-encodes them.

**What broke:** editing the canonical/og:url tags on ten pages via
`Get-Content -Raw` / `Set-Content -Encoding utf8` in PowerShell 5.1 produced a
584-line diff on `map-search.html` when the intended change was two lines. The
round-trip re-encoded every byte it could not decode, and `-Encoding utf8` in
PowerShell 5.1 also prepends a BOM. Caught before committing, reverted, redone.

**Do this instead:**

- `sed -i` from Git Bash — operates on bytes, safe for ASCII-only patterns.
- Node reading and writing with `'latin1'` — a 1:1 byte mapping, so the
  round-trip is byte-exact everywhere the script does not touch. This is the
  right tool for anything a regex can't do in one line.

**Never:** `Get-Content`/`Set-Content` round-trips, `-Encoding utf8` (BOM),
or Node with the default `'utf8'` encoding on these files.

**How to check a change went in clean**, before committing:

- `git diff --stat` — the line count must match the size of the intended edit.
  A two-line change showing hundreds of lines means the encoding shifted.
- First three bytes must not be `efbbbf` (that is a BOM):
  `head -c 3 file.html | xxd -p`
- Invalid-sequence count must be unchanged from the committed version:
  `git show HEAD:file.html | iconv -f UTF-8 -t UTF-8 >/dev/null` versus the
  same on the working copy. These files report 1 either way; that is expected
  and is not something to "fix".

Converting the whole repo to clean UTF-8 would remove the hazard, but it is a
large, risky, all-at-once change touching every page, so it has not been done.
Until it is, treat the encoding as load-bearing.

## Standing rule: new pages/tools stay hidden until Michael explicitly approves going live (added 2026-09-03)

Every new page or tool defaults to hidden, full stop — same pattern already used for the whole Dev hub (see "Hidden (non-nav) pages" below): `noindex`/`nofollow` (or `noindex, follow` once there's real citable content), no link added to `nav-partial.html`, no entry in `sitemap.xml`, discoverable only via its own `dev.html` card. That's the default for anything new, not something that has to be requested each time.

Two things this rule makes explicit, prompted by a question about the new Home Tour Route Planner (2026-09-03):

- **Building/committing a page is not the same thing as launching it.** Finishing a build, committing the files to the repo, and even Michael running `push-live.bat` (which deploys the whole site, hidden pages included) does NOT make a new page publicly visible or discoverable — as long as it stays unlinked and noindex, nothing on the live site points to it or lets Google find it, and it stays exactly that way until someone deliberately changes those three things. Michael should never need to hold off on deploying just because a brand-new, not-yet-tested tool happens to be sitting in the same commit.
- **I will never flip a page's robots meta to `index, follow`, add it to `nav-partial.html`, or add it to `sitemap.xml` on my own initiative.** That's the actual "make it live and visible" moment, and it only happens when Michael explicitly says so — I'll ask first, or wait to be told, every time, even for a page that seems finished and tested. This was already true in spirit (see the per-page "launch checklist" in the Hidden pages section below) but is now a standing rule rather than an implicit default.

Worth remembering this cuts both ways: since hidden pages are already invisible to search and to nav-driven visitors regardless of deploy status, Michael doesn't need to ask me to "keep something off the main site" as a separate step from normal hidden-page practice — that's already how every new page/tool gets built. The exception worth flagging if it ever comes up: a change to a file that's already live and linked (e.g. editing `home-value-estimate.html`) goes out with the very next `push-live.bat`, same as always — this hidden-by-default rule is specifically about *new* pages/tools, not about pausing edits to already-public pages.

- **Google Calendar "Appointment schedule"** — Free with a Google account, calendar-native (no separate sign-in for Michael), simple booking-page link to embed. - **Acuity Scheduling** (Squarespace) — Deep customization, can collect its own intake questions at booking time, client management built in. Con: no real free tier — paid plans start around $16/mo after a trial.
- **HubSpot Meetings** — Free tier available and doubles as a free basic CRM (useful side effect: every booking becomes a CRM contact), calendar sync, simple embed. Con: nudges toward the broader HubSpot ecosystem/upsells over time.
- **Cal.com** — Open-source, generous free tier, cloud-hosted or self-hostable, clean embed, calendar sync. Con: newer/less familiar in real estate specifically; slightly more setup than Calendly.
- **3veta** (Michael mentioned already having this) — Built for coaches/consultants: bundles scheduling + video meetings + payments. Worth keeping if he already has a paid account and it covers what's needed, but heavier/pricier than this use case strictly requires if Calendly/Google would do the same job for free.
- **BigMarker** (Michael also has this) — **confirmed 2026-09-01 it does NOT do 1:1 appointment scheduling.** It's webinar/event software only (registration, live/simulive hosting, follow-up email, CRM sync, AI content tools). ## Small-text readability rule — corrected twice now, treat as settled (2026-09-01/02)

**Standing rule: never combine a small font-size with a heavy font-weight on body-adjacent text.** Condensed display fonts (Barlow Condensed) at 700-900 weight read fine as short all-caps labels/headings, but become genuinely hard to read the moment they're used for a sentence or two of description text, especially at sub-1rem sizes. This has now been called out and corrected twice on `dev.html`'s "Notes & Ideas" item text (`.dev-note-item strong`/`p`) — first pass under-corrected it, second pass (2026-09-02) fixed it properly:

- Don't set a bolded label/strong element in `Barlow Condensed` at 700+ weight below ~1.1rem. If a short bold label is needed at small size, use plain `Barlow` (not Condensed) at weight 600 instead — Condensed's tight letterforms are what make heavy+small unreadable, not the weight alone.
- Body/paragraph text under a bold label should be at least 1rem, with a color no lighter than `#3d3d3d` (not `--gray-text` `#555` when the text is a primary reading block, only for secondary/muted text).
- This applies to any future callout/note-style component on the site, not just `dev.html` — check new small-text components (badges aside — badges are intentionally tiny/all-caps/uppercase and that's fine) against this rule before shipping.
- Also fixed the small low-contrast "(research reminders, not built pages)" subtitle next to the Notes & Ideas `<h2>` — bumped size and darkened its color from `--gray-muted` (#888) to `#666`. Net effect: noticeably snappier in the common case (recent location already cached by the browser/OS), but a genuinely cold GPS fix (first use, or after being off wifi/cell for a while) can still take a few seconds — that part is inherent to the device, not a bug in this page.
- No content/data changes — purely visual timing and sizing.

## AI-editing version-stamp convention — current format is `vYY.MM.DD_HH-MM-XXXX`, rolled out sitewide 2026-09-05

**A standalone quick reference for this same rule also exists at `claude/version-stamp-convention.md`** — it was split out on 2026-09-05 so a session can find the rule at the *start* of a page edit instead of hunting for it inside this 50KB doc. That file and this section are two copies of one convention and **must be kept in sync**: if the rule ever changes again, update both.

**Current format: `vYY.MM.DD_HH-MM-XXXX`** — date, underscore, time (with a hyphen between hours and minutes), hyphen, then a 4-digit revision counter, displayed with a lowercase `v`. Example: `v26.09.03_00-28-0050`. The stored `SITE_VERSION` / `MAP_VERSION` constant holds everything *except* the `v` (e.g. `const SITE_VERSION = '26.09.03_00-28-0050';`); the JS prepends the lowercase `v` when it writes the visible footer text.

**The `XXXX` counter is PER-FILE, not sitewide, and increments by 1 on every single write to that file** — trivial edits included. There is no counter file, no global sequence, and nothing to look up: the next session reads the last revision number off the file itself (any of its three stamp spots below) and adds one. Each page's own top comment block restates this rule, so every file is self-documenting on the point.

**Three spots on every edit — unchanged, no exceptions.** Every edit to a version-stamped page must update all three:
1. The `SITE VERSION:` (or `MAP VERSION:`) line in the page's top "AI ASSISTANT INSTRUCTIONS" comment block.
2. The `const SITE_VERSION` / `const MAP_VERSION` in the page's main `<script>` block.
3. The visible version text near the footer (`#site-version-display`, or `#map-version-display` on `map-search.html`).

Plus the chat-response half of the rule, also unchanged: open the reply to Michael by stating the current version (e.g. `📌 Version: v26.09.03_00-28-0050`) before describing any changes.

**Which files carry the convention (17 as of 2026-09-05):** `SITE_VERSION` on `index.html`, `find-a-home.html`, `tour-a-home.html`, `determine-your-budget.html`, `cash-to-buy-a-home.html`, `seller-net-sheet.html`, `home-value-estimate.html`, `farmstand.html`, `dev.html`, `due-diligence.html`, `utility-providers.html`, `buyer-intake.html`, `seller-intake.html`, `market-stats.html`, `financing-commandments.html`, and `tour-planner.html` (16 files), plus `map-search.html` under its own `MAP_VERSION` name. This list was originally established by a 2026-09-02 sweep of every `.html` file in the repo looking for the "AI ASSISTANT INSTRUCTIONS" marker (14 `SITE_VERSION` pages + `map-search.html` at that point; `financing-commandments.html` was added later the same day and `tour-planner.html` on 2026-09-03, bringing it to the current 17).

**Sitewide rollout of the counter format — 2026-09-05.** The `vYY.MM.DD_HH-MM-XXXX` counter scheme was introduced on `tour-planner.html` alone on 2026-09-04 (see the Sixth pass entry near the end of this doc); on 2026-09-05 Michael asked for it everywhere, and it was rolled out to all 16 remaining stamped pages. ## Per-page CSS — no shared stylesheet for page content

Every page styles itself independently in its own embedded `<style>` block (only `nav.css`/`nav.js` are actually shared, and only on guide-archetype pages — landing pages don't even include those). **Important nuance found 2026-09-02:** the `.btn`/`.btn-red`/`.btn-outline` classes used by `nav-partial.html`'s Call/Text CTAs (both the desktop `.btn-connect` dropdown and the mobile `.mob-ctas` pills) are NOT defined in `nav.css` at all — they only exist because every host page happens to define its own identical-looking `.btn{...}` (base `font-size:1.44rem`, meant for a full-size CTA button) in that page's own embedded `<style>` block, the same way `:root{...}` color tokens are duplicated per-page. ## Farmstand: pending-approvals badge on the map page (2026-09-03)

Michael wanted a way to tell at a glance whether there are new stand submissions sitting unreviewed in the Google Sheet, without opening the Sheet to check. Since `farmstand.html` already fetches the whole published Sheet CSV client-side on every page load (`CSV_URL`, via PapaParse — see `loadData()`) and the Sheet's `Approved` column already tracks exactly this (see the confirmation above: new rows land as `Approved = "FALSE"` and only count as live once that's `TRUE` or blank), the badge needed no new backend, no new Sheet column, and no extra network request — it's computed from data the page was already pulling in.

- **`countPending(rows)`** — runs on the same raw parsed CSV rows `parseCsvRows()` filters down for the map (before that filtering happens), and counts any row that has a name filled in but whose `Approved` value is present and not `"true"` (case-insensitive) — i.e. the inverse of the "is this approved?" check the map itself uses, so the two can never drift out of sync with each other. Within that pending count, it separately tracks how many have `"NEEDS ADDRESS FIX"` in their Description (the flag `addstand.gs` adds when a manually-typed address fails to geocode — see the Farmstand modal section above), since those need a different kind of attention (fixing an address) than a plain review.
- **`renderReviewPill(pending, needsFix)`** — fills and shows a small amber badge, `🔔 3 submissions pending review · 1 needs an address fix`, right below the action-row buttons (`Find Stands Near Me` / `Add a Stand` / `Reset View` / `Share this Map`) and above the category filter chips — new markup `<div class="review-pill hidden" id="reviewPill">`, styled with its own `.review-pill` CSS class (amber/gold tones, distinct from the existing `.status-bar` kinds — see below for why). **Stays hidden with zero count** — an always-visible "0 pending" badge would just be noise, so it only appears when there's actually something to look at, disappearing again once everything's been reviewed and the page is reloaded.
- **This is always visible on the live, public farmstand page** — no gating by URL parameter, no separate admin view. Michael's choice when this was proposed as three placement options (public badge / hidden behind a URL flag / on the private `dev.html` hub instead): a public badge was picked as the simplest to build and the risk is low, since it only ever shows a bare number, never any submitter names, addresses, or content — regular visitors seeing "3 submissions pending review" near the Add a Stand button, if they notice it at all, reads as ordinary site housekeeping, not as anything sensitive. Worth knowing this is a deliberate choice, not an oversight, if a future privacy-conscious pass ever questions why review-queue state is visible without gating — Michael was offered the more locked-down alternatives and preferred the plain public version.
- **Separate from `.status-bar`, deliberately:** the existing status bar (`loading`/`error`/`locating`/`demo` states) gets cleared (`clearStatus()`) once the Sheet loads successfully, but the review pill needs to persist independently of that load-state lifecycle for as long as there's a nonzero pending count — so it's its own element (`#reviewPill`) with its own always-additive show/hide logic (`renderReviewPill`), not another `.status-bar` kind that could get wiped by the next `clearStatus()`/`setStatus()` call.
- **No link to the actual Google Sheet is included** — the CSV_URL in this file is a "publish to web" pubhtml/export key, not the real editable spreadsheet ID, so there's no reliable way to construct a "jump straight to the Sheet" link from data already in the file. If Michael wants that (a direct "Open Sheet →" link next to the badge), he'd need to give me the actual spreadsheet edit URL to hard-code in.

## Site-wide form validation: real email-format + phone-auto-format, now a standing convention (2026-09-02/03)

## Password protection for `dev.html`/hidden pages — explored, not implemented (2026-09-03)

Michael asked to explore what a simple password on the Dev hub (and other hidden pages) would take to build, explicitly asking not to implement anything — pure research. Three options discussed, nothing built:

1. **Cloudflare Access (Zero Trust)** — the strongest option, and the one researched in most depth (see the follow-up section below for the specifics Michael asked about). Free tier supports up to 50 users; access is granted per-email via an "Include: Emails" policy rule (no separate password/account creation — the person signs in with a one-time code sent to their own email, or SSO); session length is configurable per policy (from immediate expiry up to ~1 month, default 24h) with an auto-refreshing signed cookie so it's not a login-every-visit experience. This wraps the whole page (or a path prefix) at Cloudflare's edge, before the page even loads — no code changes to the page itself needed.
2. **HTTP Basic Auth via a Cloudflare Pages Function `_middleware.js`** — a literal single shared password (not per-person), checked against an environment variable, triggering the browser's native login dialog on protected paths. Simpler to reason about than Access, but a single shared password stored/typed in one place is a weaker model than Access's per-person email-based access, and the browser's native basic-auth dialog is a less polished experience than Access's hosted login page.
3. **Custom login page** — a hand-built password gate (a form + a Cloudflare Function checking a password env var, setting a signed cookie) — most flexible/branded, but the most code to build and maintain ourselves versus using Cloudflare's built-in tooling for options 1 and 2.
4. **What happens with no password (the status quo)** — the current approach for every hidden page: `noindex`/`nofollow` + no nav link + no sitemap entry. This is "security by obscurity," not real access control — anyone with the direct URL (shared accidentally, guessed, found via an old link, etc.) can view it. Since none of these hidden pages contain sensitive data (no client PII, no lead data, no credentials) and the actual harm from an unintended visitor is low (at most, a competitor or curious visitor seeing an unfinished/internal tool early), Michael confirmed he's fine with this for now — see the follow-up section below.

### Crash-safe autosave — a real gap that existed until now

## Fourteenth pass — feedback provenance, cancelled stops, client itinerary + calendar, Tour Mode on a phone (2026-09-06)

### STANDING RULE: a client's rating belongs to an address, not to a slot

Client feedback is stored keyed by the stop's **index in the published order**. That
key is not stable: reorder the stops and republish, or republish a shorter tour, and
index 3 is now a different house. Nothing detected that, so a client's opinion of one
home slid silently onto another — the worst class of bug this tool can have, because
it is invisible and it is about someone's private words.

Two halves, and both are required:

1. **The server stamps every feedback entry with the address it was written about**
   (`entry.addr`, taken from the published stop at that index at write time).
2. **The planner refuses to render a rating whose stamp does not match** the stop it
   is being asked about. It shows nothing rather than showing the wrong thing.

A visible absence beats a confident lie. Entries written before the stamp existed have
no `addr` and are still trusted, since there is nothing to check them against.

Related: `clientFeedback` is now wiped whenever a different tour is loaded. `loadFeedback()`
returns early for a tour with no published page, so without the wipe the previous
client's ratings simply stayed in memory and rendered against the new tour's stops.

  1 cancelled" rather than claiming four.
- **Printed sheets** — struck through with a small "cancelled" tag, number intact.
- **Tour Mode** — jumped over by next/back; the count says "· 1 skipped".
- **Directions** — the ONE place it is dropped outright. `googleFullRouteUrl` filters

- **Export** — carried in the `.804tour.json` positional format (fields 8/9, appended,
